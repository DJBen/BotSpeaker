Our outbound single sign-on requests are signed by an authentication fleet using a private certificate stored in the secrets service. Customers’ identity providers validate those signatures using public certificates fetched from our metadata endpoint. The rotation process had two distinct changes. One updated the private key reference and asked application instances to refresh. The other replaced the public certificate in metadata. Both operations were individually valid, but the protocol only remains compatible if verifiers can accept every key that a signer might use. At 9:37, instances began refreshing asynchronously. Some loaded the new key immediately, while long-lived instances retained the old key. At 9:42, metadata switched globally to only the new public certificate. From that moment, requests signed by stale instances could no longer be validated by providers that had fetched the new metadata.

Our canary did not catch the problem because it answered a narrower question than we thought. It proved that a newly started instance could read the new secret and complete authentication through our internal identity provider. It did not sample signatures across the serving fleet, and it did not compare observed fingerprints with the certificates advertised publicly. The internal provider refreshes metadata quickly and the canary happened to reach updated instances, so every synthetic request passed while customers received a mixture of old and new signatures. The secrets controller emitted a successful refresh request event, but it did not report desired and observed versions per instance. We interpreted acceptance of work as completion of convergence.

Detection started with a general rise in external identity-provider errors at 9:46. The aggregate dashboard grouped signature-validation failures with several other provider responses and did not expose the signing fingerprint. Because failures varied by customer and our internal provider remained healthy, the initial hypothesis was a regional or provider-specific issue. At 10:17 an engineer compared a failed signed request with the current metadata and saw that the request used the retired fingerprint. That comparison was manual. The relevant information existed in separate logs, but there was no correlated view and no alert annotation connecting the error increase to the certificate change. This increased time to diagnosis even though the initial alert itself fired promptly.

The first mitigation was to restore the previous public certificate in metadata. That was reasonable under our application-deployment rollback model, but it was incomplete for this protocol. Several providers had already cached the new certificate and would not fetch metadata again for up to an hour. Reverting metadata therefore inverted the mismatch for some customers: updated signers now used a key that cached old metadata could not validate, while stale signers worked again for providers that refreshed. At 10:31 we changed strategy and decided to converge all signers on the new private key while publishing the new public certificate. We lacked a safe fleet-wide refresh command, so we restarted instances in controlled batches and watched login success, capacity, and fingerprint telemetry.

Recovery began when more than ninety-five percent of signatures used the new fingerprint at 10:52. The last stale instance left service at 11:07, and error rates returned to baseline across customer segments by 11:18. Batched replacement was slower than a fleet restart, but it protected existing sessions and kept sufficient capacity available. The responders made the right tradeoff with the tools we had. The engineering failure was that our normal rotation path could create the inconsistent state while our emergency tools could not directly measure or repair it. A safe process should not depend on responders reconstructing distributed state from logs during an outage.

The primary fix is a dual-certificate overlap protocol. At least twenty-four hours before a new private key becomes active, metadata will advertise both the current and next public certificates. Synthetic checks will verify that representative providers have fetched the dual set. The signer fleet can then roll gradually to the new private key because providers will accept signatures from either state. Every signer will report its active fingerprint as a metric and health attribute. Once one hundred percent of active instances use the new key and no signatures from the retiring key have appeared for a full external cache window, automation may remove the old public certificate. Each transition remains compatible even if propagation is slow.

We will implement the rotation as a state machine rather than a sequence of loosely coupled runbook steps. Proposed states are prepared, dual-published, provider-verified, signer-rolling, converged, retirement-waiting, and complete. Moving between states requires machine-verifiable evidence, and unsafe transitions will be rejected. The workflow will live with the authentication service code, while metadata changes are issued through a versioned interface rather than a second repository’s manual deployment. A single change record will capture current and next fingerprints, timestamps, the observed fleet distribution, provider checks, approver identity, and recovery options. Operators can pause safely in any compatible state.

Observability work is equally important. Dashboards will display signature count and failure rate by fingerprint, provider, region, and application version. The main alert will link directly to that breakdown and annotate recent rotation-state changes. The refresh controller will report desired versus observed secret versions for each instance, and the deployment UI will show convergence as a percentage with an explicit list of stale instances. Synthetic tests will cover at least three external providers with different caching behavior. We will add a diagnostic command that takes a failed request identifier and returns the signer fingerprint, advertised certificates at that time, provider metadata age where observable, and the instance configuration version.

It will verify that the target public certificate is already advertised before activating a private key. If an instance fails to refresh, the tool will drain and replace that instance while protecting fleet capacity. The command will be exercised in staging during every rotation and included in the game day. Testing must validate transitions rather than only steady states. The invariant is straightforward: every signature produced during a supported state must be verifiable by every certificate set we intentionally exposed.
